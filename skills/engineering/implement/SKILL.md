---
name: implement
description: "Implement a ticket or a spec end to end: branch, build test-first, review, pull request. Use when the user asks to implement or build an issue (`implement #42`, `implémente 42`) or a spec."
---

You write the code in this session. Spawn builders only when the work splits into large parts that touch separate files and could each be built and checked alone. A builder is a subagent on a lighter model than yours (`model: "sonnet"` in Claude Code), started with a fresh context window. It owns its part's tests and checks and reports what it built and their result: do not re-run its checks or re-read its diff beyond what the review needs.

Revert a file with `git restore <path>`, never a whole-tree `git checkout -- .`. A builder's brief says so.

1. If the user passes a ticket reference, fetch it as the issue tracker doc says under "fetch the relevant ticket", and state its title before starting. If the reference is ambiguous, ask. Without one, the work is the spec or plan in the conversation. Then post, before building, the list of what the work adds that the user sees or operates (a control, a screen state, a piece of information on screen), each with where it is already shown: the repo's design of record, the app, or the prototype the ticket names. Open that prototype to check: a prototype made for earlier work shows only what it draws. When an item is shown nowhere, stop before building its UI and ask the user to run `/prototype` in this session; build the variant they choose. Do the same when the user rejects a UI you built, rather than offering design options in the conversation.
2. List the open pull requests that change files this work is likely to change (`gh pr list` with each one's files, on GitHub). Start now regardless; only when this work needs code that one of them adds, ask the user whether to wait for it or build on its branch.
3. Start the work's branch as the repo's Branching convention says, or from the prototype branch the ticket names. With no convention, stay on the current branch.
4. List the work's acceptance criteria (a ticket's "Done when" or "Acceptance criteria"). For each criterion a test can check, write that test first and watch it fail, then the code that makes it pass, typechecking and running single test files as you go. A builder gets the criteria of its part, the working tree's path, and this same bar. Note each choice the ticket, the spec and the repo's docs leave open as you make it, with the option you set aside: the pull request lists them for the reviewer. A builder reports its own.
5. The build is done when every acceptance criterion holds and the repo's full check (typecheck, lint, tests) is green. A slow suite (end-to-end tests, packaging) runs locally only when the repo's docs say the change needs it; otherwise the pull request's checks run it. A criterion met differently, or left out, is named in the pull request, never left silent. Commit.
6. Call the Skill tool with "code-review" on the branch since its merge-base with the default branch; it sizes the review to the diff. Fix each finding, or hand it back to the builder whose part it is in (`SendMessage` in Claude Code), or record why it stays, then commit. When the branch started from a prototype branch, revert the prototype's commit last: the pull request keeps it in its history, the default branch never gets it.
7. Push and open the pull request as the repo's Pull requests convention says. Its body is written for a human who reviews code an agent wrote: it says how risky the merge is, shows the shape of the change, points at the few places to read closely, and lists the choices noted at step 4. Its body also names each open pull request found at step 2 and the files it shares with this work. End on the pull request's URL; its checks report on their own. With no convention, stop at the commit and report.
